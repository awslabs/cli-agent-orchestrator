Part of #745 / #776 (CAO 3.0, #777). Delivers #745's incremental steps 1–5 against the boundary contract in `docs/issues/745-remote-execution-boundary/design.md` (included), plus #776's interactive attach relay.

## What this does

One central `cao-server` serves N execution-only workers. Workers run `cao-bridge` (new console script): no HTTP API, no DB, no scheduler — a persistent **outbound** WebSocket to `WS /runtime/channel` (shared-token auth, fail-closed) carries everything, and anything touching the tmux socket runs in the worker. Local (non-cluster) operation is byte-for-byte unchanged.

- **Runtime channel** (`runtime_channel/`): op_id correlation + acks + retained results (a lost response is re-requested, never blindly resubmitted), `(generation, pos)` stream fencing, bounded replay with explicit gap frames, heartbeat watermarks, reconnect/hello resume, `PROTOCOL_VERSION` rejected at hello. The hello snapshot carries each live terminal's **status** as well as its stream positions, so a restarted server doesn't answer `unknown` for a terminal that has gone quiet — status is pushed on change, and an idle agent never changes. A runtime omits what it cannot read rather than claiming UNKNOWN, a hello cannot set status for a terminal it didn't bind, and a disconnected runtime still reports UNKNOWN: seeding a cache must not resurrect a stale verdict as current.
- **Routing seam**: `POST /runtimes/{id}/terminals`, `GET /runtimes`; input/key/output/status/delete for a remote terminal go over the channel; a disconnected runtime is an explicit `503`.
- **Interactive attach relay** (#776): `ATTACH_OPEN`/`ATTACH_DATA`/`RESIZE`/`ATTACH_CLOSE` plus a dedicated `attach` stream. The PTY is spawned in the runtime from the same `backend.prepare_web_attach()` the local path uses. Attach frames go to a per-terminal registry sink rather than onto the event bus — interactive bytes are a live view, not history, and republishing them would corrupt the capture stream `LogWriter`/inbox consume. `/terminals/{id}/ws` keeps its client-facing protocol byte-for-byte, so the browser terminal cannot tell remote from local, and native interactive `cao launch` attaches through that same endpoint with no client-local tmux. An unconnected runtime closes `4010` instead of appearing to attach.
- **Script relocation**: Python workflow scripts execute in the runtime (`CAO_SCRIPT_RUNTIME`) via `RUN_SCRIPT`/`CANCEL_SCRIPT`; journal/cancel/generation stay central; `CAO_API_BASE_URL` rewritten to `CAO_ADVERTISED_URL` for callbacks. Queued-cancellation recheck at the drive boundary.
- **Flow pre-scripts relocate too**, which is the second user-code path the issue names by file and line. `execute_flow` sent its pre-script through `subprocess.run` in the server container — beside the database — no matter where the agent it launches runs. It now goes over the same `RUN_SCRIPT` command, with two consequences worth stating rather than burying. First, `RUN_SCRIPT` grew a `mode`: a workflow script is Python the server runs under its own interpreter, but a pre-script is an executable file whose shebang chooses one (`docs/flows.md`'s worked example is `#!/bin/bash`), so `mode: executable` marks it `0700` and runs it directly. A v1 bridge would silently ignore that key and hand a bash health check to `sys.executable`, producing a Python `SyntaxError` blamed on the user's script — a dropped field reinterpreted as a different command, which this channel is required to refuse at connect — so `PROTOCOL_VERSION` is now `2`. Second, the remote env is **constructed** (`PATH`, `HOME`, `CAO_API_BASE_URL`, `CAO_FLOW_NAME`) rather than the server's own: forwarding `os.environ` would hand every execution pod the shared channel token and whatever provider credentials the operator set, in order to run a curl. That is a real behaviour difference for a script that reads some other inherited variable, so it is documented in `docs/flows.md` and the example README instead of being discovered. The server keeps everything it already owned — the schedule, the JSON contract, the execute/skip decision, the launch — and every unusable outcome (non-zero exit, timeout, unparseable JSON, a runtime that disconnects mid-script) raises, because none of them are `execute: false`.
- **And the session a flow launches is placed too** (`CAO_FLOW_RUNTIME`), because relocating the pre-script alone leaves the other half of a scheduled run in a container that has no tmux to put it in. It is a separate variable from `CAO_SCRIPT_RUNTIME` on purpose: a five-second health check and a long-lived agent are different workloads. The launch goes through the *same* code the HTTP route uses, extracted rather than copied — two callers each writing the registry row, the runtime binding and the reported status is two places for one of them to be forgotten, and a terminal missing its binding is a terminal nobody can route to. Recycling follows the placement: the previous run's session is torn down over the channel rather than by asking this host's tmux about a session in another pod, a busy remote conductor still blocks (read from the registry's status — `status_monitor` knows only about local panes and would call every remote conductor idle and kill a session mid-run), an unconfirmed teardown defers the run instead of launching a second agent beside the first, and rows left over from a changed placement are still handed to the local arm. Two failures are loud rather than quiet: a named-but-disconnected runtime fails the run (falling back would start the agent in the container the variable exists to keep user code out of), and a flow pinning a non-default `engine`, which `LAUNCH` cannot carry, is refused instead of silently downgraded to v2.
- **Broker bridge mode** (`CAO_ELASTIC_WORKER_MODE=bridge`): the EKS broker mints execution-only worker Deployments — **no per-worker Service or cao-server** — and the lease carries `mode`/`runtime_id`/`provider`, which `assign_elastic` routes through the central runtime path (`_assign_bridge`). "Usable" = runtime connected (`GET /runtimes`) for the caller's wait, `GATE_ON_READY`, and the reaper's never-usable verdict. The `cao worker` operator proxy keeps its allowlist but answers from the central server, scoped so one worker's id cannot resolve another runtime's terminals. Worker pods point `CAO_API_HOST/PORT` + `CAO_MEMORY_API_URL` at the central server (forwarded into MCP subprocess env; `store_lesson` now writes through the memory gateway). Server mode default is unchanged.
- **Shared-server CLI matrix** (`CAO_API_BASE_URL` opt-in): `cao schedule` and `cao memory` operate on the server's state over HTTP — never a client-local database; engine/pre-script survive a remote flow add; `cao launch` works remotely both headless and interactive, with `--runtime <id>` placing the terminal on a named execution runtime; operations that genuinely need the server's own filesystem (`terminal restore`, `memory repair/import/…`) fail with explicit errors instead of silently misrouting.
- **Shared MCP hosting**: `CAO_MCP_TRANSPORT=http` with per-request caller identity replacing process-global `CAO_TERMINAL_ID`. A new `cao-mcp-stdio-bridge` lets a stdio-only provider reach that endpoint with **no provider changes**: it proxies to the endpoint's own tool surface and turns the `CAO_TERMINAL_ID` the provider already injects into its child env into the per-request caller header. It registers no tools, holds no state and reads no database, and a missing token is fatal rather than a quiet fallback to running tools in the agent's own pod. Compatibility is driven by the official MCP SDK client over a real socket (version negotiation, two concurrent sessions with distinct identities, no identity inherited by a sequential call, a bad or absent token refused over the wire) both directly and through the shim as a child process. CLI→HTTP flow registration preserves engine/pre-script and rejects arbitrary server paths.
- **One server owner, enforced rather than assumed**: the server takes an exclusive `flock` on its state directory before `init_db` and a second one refuses to serve, naming the holder. `replicas: 1` does not prevent two servers — a rolling update overlaps pods by design — so the shipped StatefulSet is `updateStrategy: OnDelete` with a documented non-overlapping replacement procedure. flock rather than a pidfile because the kernel drops it however the holder dies, so a crashed server leaves nothing to expire by hand; scoped honestly to processes sharing a mount, which is the only case an RWO volume admits. `CAO_SERVER_OWNER_LOCK=0` opts out for local development.
- **The supervisor is now execution-only too** (`examples/cao-clusters/kubernetes/eks/`): a new `server.yaml` owns the API, the scheduler and the SQLite state, and `supervisor.yaml` becomes a `cao-bridge` pod with **no `ports:`, a headless portless Service and an `emptyDir` state volume** — so "nothing durable lives in the pod that runs the agent" is a property of the manifest, not a claim in prose. Readiness for a pod that serves no HTTP is an exec probe on a marker `cao-bridge` writes after the hello is accepted and removes on disconnect, on fatal rejection and at startup; a test parses the shipped manifest so the probe path and `CAO_BRIDGE_READY_FILE` cannot drift apart. `deploy.sh` mints `cao-runtime-token` and **refuses** to apply over the pre-#745 layout (immutable `volumeClaimTemplates`/`clusterIP`) with the exact `kubectl delete` to run, deleting nothing itself.
- **Delegation crosses the boundary at one chokepoint.** `POST /terminals/{id}/input` was remote-aware, but the *synchronous* senders inside the server were not — inbox delivery of a delegated result, agent steps, memory recall, handoff approval — and each of them typed into the server's own tmux. Routing now happens in `terminal_service.send_input`: below that branch the function is entirely about a pane on this host, and for a terminal a runtime owns the paste is worse than useless, because a local session sharing the name would receive another agent's message. Inbox delivery also stops asking the local status detector about a terminal it does not own, and classifies a disconnected runtime as transient — the message returns to `PENDING` for the reconcile sweep rather than `FAILED`, because that answer is early, not lost. Delivery runs on a worker thread, so the registry captures the channel's loop at `register()` and refuses a call made *from* that loop, where `Future.result()` would block the loop that has to deliver the frame.
- **In-session `assign` and `handoff` place their worker where the caller runs.** `POST /sessions/{name}/terminals` — the one endpoint both tools call — added the worker's tmux window in whichever container served the request, which is right while every agent shares that container and a `404 Session '<name>' not found` once the caller's session lives in a runtime pod. The session is not missing; it is somewhere else, and so is where the worker belongs. Placement now follows the caller's recorded runtime, forwarding the launch with `new_session` false so the pair are sibling windows in one session — which is what makes `send_message` without a `receiver_id` mean anything, since it routes to the recorded caller. `caller_id`, assign's deferred-init contract, `allowed_tools`, `engine` and `use_worktree` all survive the hop (the worktree is provisioned in the filesystem the agent actually runs in); `owner` is still written centrally and never handed to the executor. `idempotency_key` is refused with `400` rather than silently dropped, because no key table backs a remote launch and a retry would mint a second worker instead of returning the first. A caller bound to no runtime takes the unchanged local path.
- **Deferred work keeps an owner, and a withdrawn one stops starting new work.** A schedule fires and a queued message is delivered long after the request that created them returned, so the only other candidate for "whose work is this" is whoever the server process runs as — which is exactly the anonymisation #745's criterion 14 forbids. The canonical principal id (`issuer#subject`, from the verified token's `sub`/`iss`, or a *named* local principal when auth is off) is recorded at the moment it is known: new `flows.owner` and `terminals.owner` columns, each added by an idempotent PRAGMA-gated `ALTER`, written by `POST /flows`, `POST /sessions`, `POST /sessions/{name}/terminals`, `POST /runtimes/{id}/terminals` and the flow launch. `NULL` means *unknown*, and unknown is not revoked, so upgrading mid-week strands no existing schedule. Two decisions are load-bearing and both have tests that fail if they are undone: the owner is **never sent to the runtime** in the `LAUNCH` payload (the executor pod is the least-trusted party here, and an identity handed to it is one it could re-present — the concrete form of "agent-supplied ids are not authorization"), and it lives in **its own column rather than `terminals.metadata`**, because the `update_metadata` tool lets the running agent replace that dict wholesale, i.e. name its own owner. Dispatch is then gated where the work would begin: `execute_flow` checks before the pre-script (that script is the owner's code too) and still advances the schedule so a held flow does not re-queue every minute; inbox delivery resolves the **sender's** owner and leaves held messages `PENDING` rather than `FAILED`, so reinstatement delivers them. Revocation is deliberately asymmetric — `may_start_work` can refuse, `may_stop_work` never does — so a removed member's agent stays killable and their flow stays disableable, which is the failure mode worse than the access itself. The gate is behind an `any_revoked()` fast path, so an installation with nothing revoked pays no extra read per delivery. `owner` is also hashed into the `create_terminal` idempotency fingerprint: two principals who pick the same key (`retry`, `job-1`) must not be handed each other's live agent.
- **Provider-agnosticism is enforced, not asserted**: a static check that no `runtime_channel` module imports the providers package or names a provider id, plus one recorded `LAUNCH` contract fixture per shipped provider proving the identifier is forwarded opaquely through the shared `create_terminal` seam.

## Validation

**EKS (chaos-cluster, us-east-1, namespace `cao-745`)** — central server + bridge workers + broker:

- Server container has no tmux binary and no tmux server; sessions exist only in worker pods.
- Two workers concurrent with correct input/output/status routing; server-restart durability (DB row on PVC, routing rebuilt from the hello snapshot); killed worker → explicit `503`, never false success; teardown removes the worker session and the central row.
- Python workflow script executed in the worker pod with the callback base rewritten to the advertised URL.
- Full broker bridge cycle: lease `{"mode":"bridge","runtime_id":…}` → **no worker Service ever created** → runtime connected → central launch → task delivered → scoped operator proxy (foreign terminal refused `404`) → lease completed → Deployment reaped.
- Laptop → central server → worker pod: `cao launch --headless --runtime <id>`, plus live remote `cao schedule add/list/remove` (engine + pre-script preserved) and `cao memory list`.
- **Live provider, on cluster**: Claude Code on Bedrock in a bridge worker answered a real prompt (`● 7`, "Thought for 8s") with output routed back through the central server. Credentials come from the scoped role `cao-745-bedrock-worker`, verified in-pod as `assumed-role/cao-745-bedrock-worker` — **not** the node role.
- **Attach relay, both clients**: browser-protocol attach to that remote terminal streamed 12.8 KB of live Claude Code TUI from the worker pod's PTY through the central server, with typed input echoed into the prompt; the native CLI helper did the same under a real TTY and detached cleanly (tmux's `[detached (from session …)]` then `[detached]`, ~2.6s, no keystroke), leaving the worker session alive and no orphaned attach client.
- **Elastic cycle with a live provider end to end**: lease → pod minted with no Service and no API-server token → runtime connected → central launch → real Bedrock answer → `DELETE /workers/{id}` → `200` in 30.8s, lease `released`, `workload_present: false`, `cleanup_pending: false`, Deployment/Service/Pod all gone, runtime dropped from `GET /runtimes`, no traceback in the broker log.

**EKS, the shipped example itself (namespace `cao-745b`)** — the runs above used a stack assembled for the test; this one is `kubectl kustomize examples/cao-clusters/kubernetes/eks` rendered into a second namespace with only the substitutions this cluster forces (no gp3, no EFS, Pod Identity injection broken so a projected web-identity token stands in, Bedrock inference profiles). Both stacks are still running side by side:

- The supervisor pod **serves nothing**: no listener on `9889` from inside it or from the server, and its Service publishes no port at all (`clusterIP: None`, empty `ports`).
- Readiness comes from the marker, containing `pid 1` — the bridge *is* the container's process, which is the reason the manifest ships no liveness probe.
- A second `cao-server` started inside `cao-server-0` refused with `ServerOwnershipError` naming the holder (`pid 1 on cao-server-0`, with its start time) and exited rather than serving.
- `POST /runtimes/cao-supervisor-0/terminals` ran Claude Code on Bedrock **in the supervisor pod** and its answer came back through the server; the DB row on the server's gp2 PVC points at a tmux session that exists only in the supervisor, whose own `state` and `workspace` volumes are `emptyDir`.
- Deleting `cao-server-0` (the README's documented replacement step) withdrew the readiness marker within 3s, restored it on reconnect, rebuilt routing from the hello snapshot (`GET /runtimes` → `terminals: ["17cba9d2"]`), and the pre-existing terminal answered a fresh prompt.
- **Status now survives that restart with no interaction at all**: with the agent quiescent, `cao-server-0` was deleted; the fresh process read `unknown` while the channel was down (correct — it cannot know), then `completed` the moment the bridge reconnected, straight from the hello snapshot.
- **Full broker bridge cycle in this namespace too**: lease `{"mode":"bridge","runtime_id":"cao-worker-…"}` with the provider forwarded → **no per-worker Service created** → runtime connected in ~20s → central launch onto the leased worker → the agent's own response line (`● Tokyo`) → `DELETE /workers/{id}` → `200 {"released":true,"workload_present":false}`, lease `released`, `cleanup_pending: false`, runtime dropped from `GET /runtimes`.
- **Three execution runtimes on one server, then four**: `cao-supervisor` scaled to 3 replicas, all three connected to the single `cao-server-0` at once, each with its own tmux and none with a listener; a minted bridge worker made a fourth. After `cao-server-0` was replaced, `GET /runtimes` showed all four reconnected with their terminals rebound from the hello snapshots — `cao-supervisor-0` holding four terminals it had launched across the restart.
- **Thirteen execution runtimes, one server process** (the "1 or 10 workers, still 1 `cao-server`" criterion taken literally). Ten more `cao-bridge` pods were added alongside the three supervisors; all 13 appear in `GET /runtimes` at once. Counting by `/proc/*/cmdline` in **every** pod of the namespace rather than by manifest reading: total `cao-server` processes = **1**, in `cao-server-0` as pid 1. (A naive `ps | grep cao-server` reports supervisor pods too — those matches are the tmux command line carrying `CAO_API_HOST=cao-server…` as pane env, not a server; worth knowing before trusting the cheap check.) Routing holds at that width: `mock_cli` terminals launched on `cao-scale-5` and `cao-scale-8` bound only to their own runtimes (the other eight list no terminals), and `scale-probe-alpha` / `scale-probe-bravo` each appeared in exactly one pod's pane. Replica count is a manifest field, not a constant.
- **The supervisor delegates and receives the result, with no server of its own and nothing inbound** (#745's criterion that the restructuring exists for): a terminal launched on `cao-supervisor-0` through the central server; its agent called `assign_elastic` over the **shared MCP endpoint** (`POST /mcp 200` from the supervisor's pod IP, so the tool ran in the server pod where the broker credentials are, instead of answering "elastic workers are not configured" from a pod that holds none); the broker minted `cao-worker-63325fc9`, whose runtime dialed in and received its terminal from the central server (`POST /runtimes/cao-worker-63325fc9/terminals 200`); the worker did the work and called back from its own pod IP (`POST /terminals/4ca2f827/inbox/messages?sender_id=0b4b4075&message=757 200`); the message went to `delivered`, was typed into the supervisor's pane **in the supervisor pod**, and the supervisor's own agent read it: "The elastic worker has completed the task and returned the answer: 757." Zero `Failed to deliver` in the server log for the run.

- **Deferred work carries an owner across the pod boundary, and withdrawing one stops new work without losing any** (criterion 14). Both migrations ran against the live database on the server's PVC; all 18 terminal rows that predated them read `owner = None`, with no backfill inventing an owner nobody asserted. A launch onto `cao-supervisor-1` recorded `('b423365f','cao:local#local','{"runtime_id": "cao-supervisor-1"}')` — the owner in its own column, the metadata still holding only what the agent is allowed to rewrite — and `POST /flows` persisted the same owner on the schedule. Then `CAO_REVOKED_PRINCIPALS=cao:local#local` on the server: the flow logged `Flow owner-gate: not dispatched — owner cao:local#local is revoked` and **no** `cao-flow-%` terminal was created, while its schedule still advanced (`last_run 16:51:14`, `next_run 16:52:00`) rather than re-queueing every minute; the revoked terminal's inbox message stayed `pending`, logged as `Holding message 4 for b423365f`, not `FAILED`; and `POST /flows/owner-gate/disable` returned `{"success":true}` — stop authority survives revocation, which is the asymmetry the design argues for. Removing the variable and replacing the pod reversed it exactly: all three supervisor runtimes reconnected with `cao-supervisor-1` still holding `b423365f`, and held message 4 went to **`delivered`**. Holding is a pause, not a loss.

- **A scheduled flow's user code — the script and the agent — ran in execution pods, and the version gate proved itself on the way there** (the issue's criterion 6). Rolling `cao-server` to `PROTOCOL_VERSION 2` while thirteen v1 bridges were still connected refused every one of them at hello — `runtime channel lost (protocol version mismatch: server 2, bridge 1)` in each bridge's log, `GET /runtimes` → `[]` — so no mixed-version work was accepted at call time, which is the whole point of bumping rather than adding a field silently. The bridges withdrew their readiness markers, were replaced with the new image, and reconnected. Then `CAO_SCRIPT_RUNTIME=cao-scale-3` and `CAO_FLOW_RUNTIME=cao-scale-7`, and a flow whose pre-script is a `#!/bin/bash` file printing its own hostname. The prompt the agent actually received reads: `pre-script ran on cao-scale-3 as cao; api=http://cao-server.cao-745b.svc.cluster.local:9889; flow=placement-check; runtime token seen by the script=absent`. Four claims in one line — bash ran as bash, it ran in the script runtime and not the server, the callback URL was rewritten to the advertised Service, and the server's channel token did not cross the boundary. The agent session existed only in `cao-scale-7`'s tmux; `cao-scale-3` had no tmux server at all (the script ran there and left nothing), and neither did `cao-server-0`. The row: `('eeb2d320','cao-flow-placement-check','cao:local#local','{"runtime_id": "cao-scale-7"}')` — owner written server-side on a *schedule's* launch, criterion 14 again, through the new path.
- **Recycling followed it, including across a placement change, and a placement that could not be honoured failed loudly.** A second run tore the first session down in its runtime and left exactly one row, with `cao-scale-7`'s tmux session recreated (created 19:29:04 → 19:30:18). Moving `CAO_FLOW_RUNTIME` to `cao-scale-0` moved the session: nothing left running in `cao-scale-7`, `cao-flow-placement-check` present in `cao-scale-0`, one row pointing there. Pointing it at `cao-scale-99`, which does not exist, returned `flow placement-check: remote launch on runtime 'cao-scale-99' failed: runtime 'cao-scale-99' is not connected` — with the previous session still torn down, **no** session created in the server container and no orphan row left behind. The run fails; it does not quietly start the agent beside the database.

- **A terminating executor now says so, which is how the shutdown half of the placement criterion got its first real measurement.** `Bridge.stop()` set its stop event and nothing watched it — `_serve` parks on `async for raw in ws` — so a pod being deleted kept its readiness marker and its channel until the kubelet's SIGKILL. Measured on the cluster with the shipped 30s grace period: the pre-fix image left the runtime in `GET /runtimes` for **33s** after the delete; the fixed image removed it in **~2s**, with the bridge logging its own exit 1.5s after the signal. `stop()` now closes the socket, which runs the reconnect loop's `finally`. Two tests, and dropping the close turns one of them into the timeout it exists to catch. The README gained the section this belongs in — every workload's `requests`/`limits` including the broker-minted worker, the 30s on both sides and the broker's wait derived from it, and what grace does *not* buy: a live agent turn is not resumable.

- **Two more defects the cluster found after that, both fixed here.** Re-running the placement flow once its executor had been replaced wedged it: the central row survived, the runtime came back empty, and `deleted: false` was read as a cleanup that might have left an agent running — correct posture, wrong input, and it would have deferred on every later run forever. `TEARDOWN` now separates "nothing here to tear down" (`absent`, reported by a runtime with no row for the id) from "I could not finish" (still a failure, because a session that may be alive must never be declared gone); the server settles the row and routing on the first and still raises on a timeout. Verified by reproducing the exact precondition — executor deleted while the server stayed up, the binding surviving the reconnect — and the run that had been stuck returning `{"executed":true}` with the stale row cleared. And every remote launch had been logging `Error in StatusMonitor: Terminal … not found in database` tracebacks: the server was regex-scanning republished bytes from other pods to reach a verdict the registry already holds from the runtime that owns the pane, before the central row even lands. It now skips terminals the registry calls remote, and treats a chunk for an unknown id as nothing to attribute rather than an exception. Measured as an A/B on one server pod against the same executor: a launch plus a turn logged 6 of those tracebacks before the fix and none after, with the terminal still reaching `completed` from the runtime's own verdict. 10 tests between them, every guard mutation-checked.

- **A third one, from watching the version gate hold.** Two executors were deliberately left on the v1 image after the server moved to `PROTOCOL_VERSION 2`. The gate behaved: both sat at `0/1`, neither appeared in `GET /runtimes`, no work reached them. What that also showed is that they were retrying **once a second, for hours** — 6346 log lines from one pod. The reconnect backoff was reset as soon as `websockets.connect` returned, and every *permanent* failure is raised after that point, so the doubling could never happen for the one case it matters for. The reset now requires a completed hello, which is the condition the readiness marker already used, for the same reason: a socket that opened is not a runtime that works. Measured by dialing the live server from an executor pod with a bumped version: **60 attempts in 60s** (all gaps 1.01s) before, **7 in 90s** with gaps `1, 2, 4, 8, 16, 30` after. A runtime that lost a channel it had been serving still returns in about a second — that arm is a test of its own, and each of the two fails under the opposite mutation.

- **A fourth one, from driving the operator surface by hand.** Asking the live cluster what was running, from a laptop: `GET /sessions` and `cao session list` both answered "no active sessions" while five agents were bound to runtimes. `list_sessions` was built entirely from `backend.list_sessions()` — the *server's own* tmux, which a shared `cao-server` does not run at all. Every other session-scoped operation reads the database and was already right remotely (`session status`, `session send`, `GET /sessions/{name}/terminals` each verified from the laptop); only the enumeration was blind, and it failed in the shape this PR is otherwise careful about — a confident wrong answer rather than an explicit one. The listing now unions the backend's sessions with those the registry's terminal→runtime bindings place in a runtime, tagged with the runtime ids executing them; liveness comes from the bindings rather than the rows, because a row outlives its runtime and a binding does not. A session the backend already reports is not listed twice, so a hybrid host is unchanged, and the pane-cwd fallback is skipped for a remote terminal — on a hybrid host it would otherwise report a local directory as a remote agent's cwd. Verified by rolling the server onto the fixed image: the same call that returned `[]` returns the 4 live sessions with their runtime ids, `cao session list` renders them with conductor and status, and one stale binding with no central row is dropped rather than failing the listing. 16 tests, 7 mutations checked, including both directions on the cwd guard.
- **A fifth one, from running `examples/assign/` on the cluster with real agents.** The supervisor's every `assign` and `handoff` came back `404 {"detail":"Session 'cao-cluster-assign-745' not found"}` while that session was demonstrably alive in `cao-supervisor-0` — the in-session orchestration surface, the thing the examples directory is built on, did not work at all across this boundary. `POST /sessions/{name}/terminals` added the worker's tmux window wherever the request was served, which was the right answer while every agent shared that container. The session is not missing; it is in a runtime pod, and so is where the worker belongs. Placement now follows the **caller's** recorded runtime: if `runtime_for_terminal(caller_id)` names one, the launch is forwarded there with `new_session` false, so the worker lands beside the agent that asked for it in the same tmux session — which is what makes the pair siblings for `send_message`/inbox routing. Everything that request carries had to survive the hop (`caller_id`, assign's deferred-init contract, `allowed_tools`, `engine`, `use_worktree` — the worktree is provisioned in the filesystem the agent actually runs in), while `owner` is still written centrally and never sent to the executor. `idempotency_key` is **refused with 400** rather than silently dropped: there is no key table behind a remote launch, so honouring it would promise a retry returns the first worker when it would produce a second. A caller bound to no runtime takes the unchanged local path, so a single-host install is untouched. 4 tests. Measured with Claude Code on Bedrock: before, every assign 404'd and no worker existed; after, supervisor `dabd53c5` plus workers `ff8fff81` (`data_analyst`) and `4294b1b1` (`report_generator`) all in session `cao-assign-745` with `caller_id=dabd53c5` and `metadata.runtime_id=cao-supervisor-0`, three `claude` panes in that pod's `tmux list-windows`, the handoff's `report_template.md` written inside the pod, both callbacks `delivered` to the supervisor's inbox, and a combined report matching the input CSV (South $121,500 best region, March $89,000 strongest month, $244,500 total).

The delegation run is what found the delivery defect fixed above, and the first attempt at it is worth recording because the failure mode was quiet: the lease settled, the worker's answer reached the server — `POST /terminals/ef38cd1c/inbox/messages?…&message=757 200 OK` — and then `Failed to deliver message 1 to ef38cd1c: Session 'cao-2b412d60' not found`. The server had queued the message correctly and typed it into its *own* tmux, where the supervisor's session does not exist; the message was marked `FAILED` and the supervisor never learned the answer. Delegation looked like it worked from every signal except the only one that matters.

Running that cycle first against a **stale broker image** reproduced the 15s release bug verbatim, which is a fair check on the fix rather than on the claim: `broker.py:848`, `deadline = time.monotonic() + 15.0`, `TimeoutError: worker … Deployment was not deleted within 15s` answered as HTTP 500 while the pod was in fact already `Terminating`. The branch's `WORKLOAD_DELETION_TIMEOUT = WORKER_TERMINATION_GRACE_SECONDS + 15` answers `200` for the same teardown.

The broker cycle is also what exposed the status-on-reconnect gap fixed above: routing came back correctly and `GET /terminals/{id}` still read `unknown`, because the restarted server had never seen a status frame for a terminal that had stopped moving. It was found by validating on a cluster, not by a test; it now has eight, and the three non-behaviours are mutation-checked.

Two things the first live-provider run exposed, both fixed here:

- Where EKS Pod Identity is not injecting, a worker pod silently falls back to the **node** role and the only symptom is a `403` from Bedrock naming the node instance role. `CAO_ELASTIC_WORKER_IRSA_ROLE_ARN` (opt-in, unset by default) makes the broker project a web-identity token onto every worker it mints; `automountServiceAccountToken` stays off either way.
- `_release` waited a flat 15s for the Deployment to disappear against the worker pod's own 30s `terminationGracePeriodSeconds`. With `Foreground` propagation the Deployment outlives its pod, so that threshold was unreachable for any worker that does not exit instantly on SIGTERM — and a bridge worker running a real agent does not. A teardown that had in fact removed everything answered HTTP 500 and the lease read as `cleanup_pending`. The wait is now derived from the grace period plus headroom; a workload that genuinely survives is still reported rather than silently accepted.

### What review found that the cluster could not

Copilot raised 13 findings on this PR. Twelve were real and are fixed here; each needs a race, a restart or a second client to show itself, which is why live runs missed them. One was not a defect as stated, and saying so is part of the answer: the `generation` fencing finding cannot be fixed as written because nothing in the codebase ever advances that field. The harm behind it is real, so it is fixed by the check that actually holds today: the identity of the registered connection.

- **The channel credential was reaching code CAO does not ship.** Two providers build an MCP child env by hand and merged the shared-endpoint env into *every* entry they write, so an agent profile's or plugin's own server got `CAO_RUNTIME_TOKEN` for no purpose — and both files that persist such an entry (`mcp_config.json`, `opencode.json`) are re-read at every later launch, so the token lived in a umask-default world-readable file. The forwarding env is now gated on the command, and a file CAO creates is owner-only.
- **`cao launch` was the one remote CLI path that addressed the wrong server.** It used the import-time local `API_BASE_URL` and sent no bearer token, so against a shared server it either talked to whatever listens on this machine's port or was refused as anonymous — with the interactive case refusing the WS attach *after* creating the terminal.
- **A reconnect left the channel it replaced still being read**, republishing stale output as live and advancing the resume watermark so the live channel's real output was skipped as already-seen. **A second attach client** parked the one it displaced on a queue nothing would feed again, then closed the PTY the replacement was reading. **`remote_terminal_ids`** answered a liveness question with routing state, so `GET /sessions` listed a dead pod's sessions as active indefinitely. **LAUNCH** now opens the replay buffer instead of waiting for a first byte, so a pane that has not spoken yet is in the hello snapshot.
- **`CAO_SCRIPT_RUNTIME` degraded to local execution when its runtime was down** — running author-supplied code in the server container beside the database and every credential the server holds, reported as a success, which is precisely the outcome the setting exists to prevent. It now fails the run, as the design, the runbook and the sibling `CAO_FLOW_RUNTIME` path all already said. Relatedly, a **relative `script:` path is refused at `cao schedule add`** against a shared server rather than resolving, hours later, against a directory the server has never seen.

Three further review rounds raised thirteen more. Twelve were real and are fixed as described; the thirteenth is real in its harm and wrong in its proposed remedy, which is set out below rather than quietly reinterpreted. The list also revisits one round-one finding this description had defended and should not have. Several share a shape worth naming: they are correct against the configuration a developer runs and wrong against the one an operator deploys, so no amount of local exercise would have surfaced them.

- **A runtime was creating the control plane's entire schema.** `cao-bridge` executes panes and owns no orchestration state, but it called `init_db` — the *control-plane* initializer — so every execution pod created and migrated workflow journals, memory, the vault and handoff results on its own SQLite file. That is worker-local state that reads as authoritative and is not, which is the case the topology contract exists to rule out, plus a migration registry running where nothing will ever read it. An earlier revision of this description defended that call; it was wrong, and the correction is `init_runtime_db`, which creates only `terminals`, `inbox` and `idempotency_keys` and runs only the two `terminals` migrators so a pod rolled forward onto an older file can still query it. 21 tests, including the `init_db` contrast so the absence assertions cannot pass for the wrong reason.
- **60 calls to `cao-server` carried no credential.** `api_request` attaches the bearer token, but that many call sites across the CLI, the MCP server and orchestration assembled their own `requests.get`/`post` against `API_BASE_URL` without `headers=`. Every one worked against the default-off local server and returned `401` the moment an operator enabled auth — the single deployment nobody had exercised. The omission is invisible at the call site and silent in every local test, so the rule is now pinned by a test that walks the source rather than the calls: every `requests.<verb>` in the package passes `headers=`. The one exemption is the install-profile download, which goes to an allowlisted *public* host and must not be sent CAO's token at all; the test also fails if that exemption stops matching a real call, so it cannot decay into a blanket licence.
- **A bounded gap left the resume position behind the bytes that are gone.** A `GapFrame` with `to_pos` set is a definitive loss. The server reported it to subscribers but did not advance the watermark, so the next reconnect asked the runtime to resume from a position inside the lost range and the stream stalled there. The bounded arm now records the gap's end; an unbounded gap (lost generation, no known extent) still must not advance, and `record_position` stays monotonic, so a stale or duplicated gap cannot rewind a watermark that has already moved on.
- **A config file holding a token was published world-readable.** The generated `opencode` and `antigravity` configs carry API keys and MCP credentials and were written through the mode-*preserving* atomic write, so a default umask left them at 0644 and an existing 0644 file stayed that way. `write_owner_only` creates the temp file at 0600 by construction — `mkstemp`, not a `chmod` afterwards — so the bytes are never reachable at a wider mode, not even in the window before the rename. `locked_atomic_write` keeps preserving the target's mode; that is the right contract for the files it writes and the wrong one for these.
- **The shared MCP endpoint's token gate covered `tools/call` and nothing else.** FastMCP dispatches method-specific hooks under `on_message`, so a check in `on_call_tool` left `initialize` and `tools/list` ungated: an unauthenticated client could open a session and enumerate the whole tool surface — every name, description and argument schema — learning the shape of the control plane before being refused at the first call. The gate moved to `on_message`, where "every request carries the token" is actually true, and is still re-checked in `on_call_tool` because an authorization gate should not depend on another layer having run first. Asserted from the endpoint's own round trip rather than from the helper in isolation.
- **A headerless request on the shared endpoint borrowed the hosting process's identity.** `resolve_caller_terminal_id` used `None` both for "no request in flight" and for "a request that named no caller", so on a shared endpoint whose process happened to have `CAO_TERMINAL_ID` set, a request with no caller header was silently attributed to that terminal and could run caller-scoped tools as it. An explicit anonymous sentinel now separates the two: a request that names no caller resolves to `None` and the env var is not consulted, while the stdio path — one process per agent — still reads the env byte-for-byte as before.
- **A pre-script that exists only in the runtime was documented as supported.** `docs/flows.md` said `CAO_SCRIPT_RUNTIME` lets the code live in the runtime, but the server reads `script_path` and sends its *contents*, so a runtime-only path fails with `Script not found` before anything is dispatched. The doc now states the actual contract — the runtime never needs a copy, but the server does need the original — rather than promising a placement the implementation refuses.
- **The owner lock's re-entry was not per state directory.** The reference count accepted *any* second `lock_path` while it held one, so an embedded or test server started for a different `CAO_HOME_DIR` was told it owned that directory without ever locking it — leaving the second state free for another process to own at the same time, which is precisely what the lock exists to prevent, arriving through the mechanism that makes the safe in-process case work. Claims are now keyed by resolved path: re-entry counts only for the directory already held, a different path takes a real `flock` of its own, and the test proving it starts a genuinely separate process that must be refused. Releasing one directory leaves the other held.
- **The heartbeat's watermarks were discarded — and adopting them would be worse.** The heartbeat carries each stream's `end_pos` so the loss of a *final* chunk is detectable when no later output ever arrives (#776), but the handler rebound routing and threw the positions away, so nothing acted on the one signal that carries them. The review's remedy was to persist the advertised position; that is the one thing this must not do. The recorded position means "bytes the server has actually received", and those undelivered bytes are still sitting in the runtime's replay buffer — `Bridge._send` swallows a `ConnectionClosed`, which is exactly how a chunk goes missing while the buffer keeps it — so the stale watermark is what makes the next reconnect replay them. Advancing it would mark unreceived output as received and discard the only path that recovers it, converting a recoverable shortfall into silent loss. If the range is evicted before that reconnect, the reconnect's bounded `GapFrame` declares the loss and moves the watermark; the runtime is the only party that knows the bytes are gone, so that is the path allowed to say so. The fix is therefore to state the discrepancy and leave the watermark alone — once it has survived two consecutive heartbeats without progress, because a reconnect's replay is a stream of chunks a heartbeat can interleave with, and a warning that fires during ordinary recovery is one operators learn to ignore. Seven tests, and the reviewed alternative is itself mutation-checked: adopting the advertised position fails three of them.

- **A hole inside the replay window was reported once and then forgotten.** `append_at` returns the gap the live path turns into a `GapFrame` — but a chunk is dropped precisely when things are going wrong, and if the channel is already down that frame is never sent. The consumer then reconnects from the end of the last chunk it *did* receive, which is inside the retained window, and `replay_from` only looked for a gap before `window_start`: the higher-positioned chunk replayed as though it followed contiguously, the server recorded its position, and a transcript with a hole in it was accepted as whole. Gaps and bytes now come back interleaved in stream order. Chunk starts are the authority, so a hole needs no new bookkeeping to detect, only to be looked for — and the order is part of the fix, because emitting every gap first would advance the server past bytes it has not received and reintroduce the same silent loss one layer up.
- **The native attach put the bearer token in the URL.** `cao launch`'s WS attach sent `?token=`, which the server accepts only because a browser cannot set a header on a WebSocket handshake. uvicorn logs the raw path and the access log's redaction was keyed on `access_token`/`ticket`, so the one client that *could* send a header instead persisted a reusable credential in plaintext, in this process's log and in any proxy's. It now sends `Authorization: Bearer`, and `token` is redacted as well for the viewer that has no alternative.
- **Claude's per-terminal MCP config was published at the umask default.** That file can carry `CAO_RUNTIME_TOKEN` — `resolve_mcp_server_config` hands the bundled server the channel credential — and `write_text` then `chmod` flushes the whole body before narrowing it, leaving a pre-existing inode at its old mode for the duration of the write. Same `write_owner_only` as the configs above. MiniMax's plugin config is written into a tree recreated at 0700, so it is not reachable the same way and is unchanged; saying so is part of the finding rather than a silent omission.
- **The status monitor's "unknown terminal" guard also swallowed misconfiguration.** `get_provider` raises `ValueError` both for "no row for this id" — ordinary on a central server, which sees bytes on either side of a row's life — and for a row whose provider *refused to be built*: an unknown provider type, a kiro profile with no agent. Catching the base class treated the second as the first, so a local terminal silently never accumulated a status buffer and nothing was logged. The missing row now raises `TerminalNotFoundError`, a `ValueError` subclass so every other caller is unchanged, and only that is caught.

Two hermeticity bugs were found while re-running the suite for these rounds rather than by review. The server owner lock defaults to the real state directory, so any test driving the app lifespan contended with a `cao-server` running on the same machine — 25 failures on a developer laptop, none in CI. The lock is now redirected per session, with the one test whose subject is the lock's location still asserting the shipped path. And `TestGrokCliSkills` was missing `@pytest.mark.e2e`, so a plain `pytest` run collected it, which fired the session-scoped autouse fixture in `test/e2e/conftest.py`: that boots a real server subprocess and rewrites `constants.API_BASE_URL` to its ephemeral port for the rest of the session. The visible casualty was in another directory — a `test/mcp_server` assertion comparing against `API_BASE_URL` — with nothing in the traceback pointing back at the e2e conftest. The marker is restored, and a path-scoped `pytest_collection_modifyitems` in that conftest now marks by location so the next missing decorator cannot do it again.

**Local** — full suite green: `11549 passed, 33 skipped, 1 xfailed` (no test deleted or rewritten — no `def test` line is removed anywhere in the diff; the later review rounds added tests, they did not replace any). One pre-existing test is excluded from that run and is not this PR's to fix: `test/services/test_script_lint.py::test_deeply_nested_expression_is_total` feeds `lint_script` a 200 000-deep attribute chain, and on CPython 3.10 with an 8 MB stack `ast.parse` segfaults the interpreter rather than raising — it kills the run wherever it appears, on this branch and on `3.0-beta1` alike (measured: 100 000 parses, 200 000 crashes). Standalone broker suite green in both modes (197 checks, including a fake-clock test that reproduces the 15s release failure and passes with the fix). `kubectl kustomize` renders the EKS example clean in both the Bedrock default and the kiro overlay.

Four behaviours added late were mutation-checked rather than assumed: dropping the MCP caller header, skipping the shared-token check, removing the ownership guard, and swallowing an ownership conflict are each caught by a test that fails.

Three claims here were implemented but had no test until a pass over the acceptance criteria caught them; each new test was checked against a mutant that removes the behaviour, and each fails fast rather than hanging:

- **Concurrent multi-runtime routing.** Every existing registry test registered *one* runtime, so a registry that ignored `runtime_id` entirely would have passed. Four tests now connect two runtimes and assert input and cancel reach only the owning runtime, that one runtime dying leaves the survivor's status and channel intact, and that stream positions are per terminal. A mutant resolving the first connected channel instead of the bound one fails three of them.
- **`PROTOCOL_VERSION` mismatch at hello** — implemented on both sides, but every test built its hello from the same constant, so the rejection arm never ran.
- **Reconnect recovery on the bridge side** — retained results re-delivered, each stream resumed from the server's position, eviction reported as an explicit gap.

## Known limitations, stated rather than implied

- **A pod that runs an agent can no longer be told apart from a caller at the network layer.** This is the one property the restructuring gave up, and it is the reason `cao-supervisor-ingress` is gone: an execution pod's channel is outbound and its MCP tools dial `cao-server:9889` directly, so `cao-server-ingress` must admit it. A prompt-injected agent can therefore reach control routes the broker's five-route gateway used to withhold, bounded by the shared `CAO_RUNTIME_TOKEN` plus the server's per-request caller identity — an application-layer boundary where there used to also be a network one. #774 closes it with per-runtime delegated credentials; until then, possession of the token is possession of the control API — and the agent does possess it: the executor pod's env holds `CAO_RUNTIME_TOKEN` so the bridge can dial the channel, tmux propagates that env into the agent's pane, and `ps` inside the pod prints it. Nothing here reduces the blast radius of a prompt-injected agent below "whatever the shared token can do". Recorded in `networkpolicy.yaml` and in the example's README rather than left to be discovered from a policy diff.
- **The provider conformance fixture patches `create_terminal`** — it proves the identifier travels opaquely, not that an agent ran. The live provider runs above were manual; there is no automated non-mock gate, and the `live_provider` marker in `pyproject.toml` is currently unused.
- **Criterion 14 is delivered as far as #745 can deliver it.** What is here is the carrying and the gating: the owner survives the queue, the schedule and the cross-pod callback, and revocation stops new work without taking away the authority to stop existing work. What is *not* here is the trusted record it should read from — there is no tenant model, no membership store and no removal workflow, because #774 (per-runtime delegated credentials), #778 and #779 own those and are still open. Until then the revocation list is operator-supplied (`CAO_REVOKED_PRINCIPALS`), the issuer is trusted transitively via the token the server already verifies, and a `tenant` key in the principal document is tolerated on read but nothing writes one. Stating it plainly: this makes the criterion's *behaviour* testable and tested, not its identity source of truth.
- **No provider ships with `CAO_MCP_TRANSPORT=http` as its default.** The shared endpoint and the stdio shim are available and tested; wiring a provider to prefer them is a separate change.

Three limitations listed in an earlier revision of this description are now closed rather than shipped as caveats: the supervisor no longer runs a `cao-server` or an inbound Service (see `server.yaml`/`supervisor.yaml` above), single ownership is enforced by the owner lock rather than resting on the deployment shape, and the stdio→HTTP shim exists with an MCP-SDK round-trip test behind it.

One pre-existing unrelated failure: `test/services/test_script_lint.py::TestSyntaxRule::test_deeply_nested_expression_is_total` segfaults on macOS/CPython 3.10 (`ast.parse` overflows the C stack). It reproduces unchanged on the parent commit and is deselected in the runs above.

## Not in this PR

Per-runtime delegated credentials (#774) — the runtime channel and the shared MCP endpoint authenticate with a shared `CAO_RUNTIME_TOKEN`, fail-closed, until #774 supplies per-caller credentials whose verified subject replaces the token and caller header.
